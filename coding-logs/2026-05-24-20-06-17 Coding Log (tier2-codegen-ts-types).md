# Tier 2 Codegen TS Types

## Plan Draft A - Local Generator Beside Schemas

### Overview
Add a repo-local TypeScript generator that reads JSON schemas and writes deterministic `*.types.generated.ts` modules beside those schemas. Wire the Greenfield API code to consume the generated record types instead of manually duplicating schema shapes.

### Files to Change
- `scripts/codegen-schema-types.ts` - CLI and reusable generator for the supported JSON Schema subset.
- `schemas/greenfield/user.types.generated.ts` - generated TS types for `user.schema.json`.
- `services/api/src/db/schema.ts` - derive record kind and schema record types from generated output.
- `services/api/src/db/seeds.ts` - consume generated user/project record types.
- `tests/api/schema-codegen.test.ts` - verify generator output and drift checking.
- `scripts/run-api-tests.mjs` - add `schema-codegen` alias.
- `package.json` - add codegen/check scripts.

### Implementation Steps
TDD sequence:
1. Add/stub `tests/api/schema-codegen.test.ts` expecting generator exports and generated output.
2. Run `npm run test:api -- schema-codegen` and confirm it fails because the generator/generated module is absent.

4. Refactor minimally only where manual types are replaced by generated types.
5. Run `npm run codegen:schema-types`, `npm run check:schema-types`, `npm run test:api -- schema schema-codegen seeds`, and targeted typecheck if feasible.

Functions:
- `generateTypeModuleFromSchema(schema, options)` converts the known schema subset (`oneOf`, `$defs`, `$ref`, object properties, `const`, strings) into stable TS text.
- `generateSchemaTypes({ check })` writes or compares all configured schema outputs.
- `typeNameFromDefinitionName(name)` normalizes JSON Schema definition names to exported TS identifiers.

Expected behavior and edge cases:
- Deterministic formatting and sorted configured outputs.
- Fail closed on unsupported schema shapes so generated types do not silently drift.
- Check mode exits non-zero when generated files are stale or missing.

## Plan Draft B - TypeBox Source of Truth

### Overview
Replace the handwritten JSON schema with a TypeBox source module and emit both JSON schema and TS types from that module. This would make TypeScript the schema source of truth.

### Files to Change
- `services/api/src/db/schema-source.ts` - TypeBox declarations for user/project records.
- `scripts/codegen-schema-types.ts` - emit JSON schema and TS aliases from TypeBox.
- `schemas/greenfield/user.schema.json` - generated output rather than author-owned schema.
- Current service/test files - consume TypeBox-derived types.

### Implementation Steps
TDD sequence:
1. Add tests proving JSON schema output remains byte-for-byte stable.
2. Confirm tests fail because TypeBox source/generator is absent.
3. Implement TypeBox schema source and emit both schema and TS types.
4. Replace manual service types with TypeBox static types.
5. Run schema, seed, and full Greenfield validation.

Functions:
- `buildGreenfieldPersistenceSchema()` returns TypeBox definitions.
- `writeGreenfieldSchemaArtifacts()` writes JSON schema and TS types.

Expected behavior and edge cases:
- TypeBox becomes the single source of truth.
- Existing public JSON schema must remain stable.
- Unsupported JSON Schema hand-authored features become harder to preserve.

### Test Coverage
- `schema-codegen.test.ts / preserves public JSON schema bytes` - prevents contract churn.
- `schema-codegen.test.ts / emits TypeBox static record types` - proves TS types derive from source.

### Decision Completeness
- Goal: one TypeScript schema source emits JSON schema and types.
- Non-goals: runtime validation replacement, migrations, external API changes.
- Success criteria: public schema unchanged and types compile.
- Public interfaces: TypeBox source module plus generated artifacts.
- Edge cases / failure modes: schema byte churn fails closed; TypeBox limitations may block exact schema preservation.
- Rollout & monitoring: no runtime rollout; CI watches schema artifact drift.
- Acceptance checks: schema byte preservation test and API tests pass.

### Dependencies
Uses existing `@sinclair/typebox`.

### Validation
Run generator, schema tests, seeds tests, and Greenfield unit validation.

### Wiring Verification
| Component | Entry Point | Registration Location | Schema/Table |
|-----------|-------------|----------------------|--------------|
| TypeBox source module | generator and service imports | import statements | `schemas/greenfield/user.schema.json` output |
| schema artifact writer | npm script | `package.json` scripts | public JSON schema |

### Cross-Language Schema Verification
No DB or cross-language table change.

### Decision-Complete Checklist
- Public surface listed.
- Tests cover schema preservation.
- Risk remains around unnecessary source-of-truth inversion.

## Comparative Analysis
Draft A is smaller, preserves JSON Schema as the explicit source of truth, and directly addresses the open Tier 2 item. Draft B is attractive longer term if TypeScript should become the schema authoring language, but it widens scope and risks public JSON schema churn. Draft A better matches the requested item and project rule to keep changes small and reversible.
